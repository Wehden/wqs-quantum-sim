## Pulses and solver work

Recommend exact support segmentation for plain square pulses. A square must not silently become the trapezoidal interpolation approximation used to characterize the native array interface. Preserve the state between segments within the same job, and preserve the first-time reference for propagators. This does not create cross-job state or automatic job chaining.

For smooth and sampled envelopes, use linear numeric interpolation with a grid containing output times, exact support boundaries and supplied knots. Proposed limits are 65,536 knots and 16 coefficient channels. Curvature and operator-norm bounds must certify integrated generator error; grid doubling is an additional diagnostic, not a proof by itself. Propose a coefficient approximation budget of 1e-6 in the relevant SE state norm / ME trace norm, separate from the solver error budget. MC certification applies to the generator and interpolation, not a noisy sample-versus-sample comparison. Reject an unresolved request rather than coarsening its pulse silently. TASK-012 must prove the supported shapes and their refinement/refusal policy.

**Owner choice:** defer DRAG and positive square rise from version 1 until their sign/units/edge definitions and dedicated tests are approved. Constant, plain square, Gaussian, flattop and sampled envelopes remain targets; deferral does not authorize advertising untested shapes. The alternative is to accept the design's explicit `beta`-in-ns and symmetric cosine-edge conventions and add the corresponding tests before admission.

Native work accounting is a remaining contract item, not a completed discovery claim. QuTiP's explicit RK loop bounds accepted and rejected trials per native advance; its MC outer loop can repeatedly advance and reset. `nsteps` therefore does not establish one universal job-wide RHS bound. The adapter must account for the chosen tableau's state buffers and finite native work across all trajectories/refinements; tests must cover collapse searches, resets and exhaustion. A trusted job-wide ledger is a candidate mechanism, requiring a source-verified charge model and measured policy before it is frozen. No new simulation wall-time limit or global job-count cap is proposed. Existing cancellation remains available. A caller-supplied coefficient function, native option dictionary or executable callback is never accepted.

Sources: [pinned explicit RK implementation](https://github.com/qutip/qutip/blob/v5.3.1/qutip/solver/integrator/explicit_rk.pyx), [pinned MC implementation](https://github.com/qutip/qutip/blob/v5.3.1/qutip/solver/mcsolve.py). `vern7` needs 10 integration stages and 16 stages with dense interpolation, plus other live state buffers; do not reuse an eight-array workspace estimate as its worst case.

## Exact result envelope proposal

Use uncompressed numeric NPZ, with a scalar Unicode `metadata_json` and no object arrays or pickle. Proposed limits:

- At most 6 MiB of numeric payload, 64 total members including metadata, ASCII member names up to 64 characters and rank at most four.
- Metadata JSON at most 64 KiB UTF-8; count its actual NumPy Unicode storage as `4 * len(metadata_json)`, bounded by 256 KiB.
- Summary JSON at most 64 KiB. Count actual escaped/encoded bytes, not characters.
- Bound each NPY header to 4,096 bytes and reserve 256 bytes of ZIP/name overhead per member plus 1,024 archive bytes. Validate the emitted archive against this formula.

A conservative complete NPZ bound is `B = numeric_bytes + 4*metadata_characters + 4352*member_count + 1024`, at most 6,833,152 bytes at these ceilings. Base64 is exactly `4*ceil(B/3)`, at most 9,110,872 bytes. With the bounded summary and 256 bytes of callback JSON framing, the complete numerical output file is at most 9,176,664 bytes, below the existing 12-MiB file and artifact-field limits and 16-MiB request limit. These totals include metadata and archive overhead; compression is not assumed.

TASK-008 must verify NumPy's actual header/ZIP framing and worst-case Unicode/summary escaping, charge simultaneous serialization copies, and reject any emitted object exceeding its planned bound. If the measured encoder violates the formula, admission remains closed until the formula or encoding is corrected. Existing circuit archives, summaries and canonical bytes remain unchanged.

## GPU decision: awaiting bounded hardware diagnosis

All GPU work must be scheduled through the existing SkyPilot API server. The direct Runpod Serverless test transport was withdrawn after the owner clarified this requirement. Its retained historical receipts cannot close scheduler acceptance. The test budget is $25 total; SkyPilot owns allocation and automatic teardown. Existing local GPU consumers and credentials remain outside its scope.

The SkyPilot-scheduled cloud CPU suite passed all 12 fresh children / 48 checks. On the same worker, all 12 GPU numerical children failed during CUDA initialization with `cudaErrorMemoryAllocation` under the existing 3-GiB AS bound. No simulator GPU computation occurred. The corrected job wrapper propagated the failures and SkyPilot reported `FAILED`; subsequent SkyPilot teardown and status readback confirmed termination.

The SkyPilot RTX4090 diagnostic now initializes at 8/16/64 GiB AS and fails at 3 GiB. At 8 GiB, virtual size is about 4.37 GiB while RSS is about 495 MiB. The assigned card had 1 MiB in use before initialization. These controlled results establish an AS-bound incompatibility on the tested configuration; they do not establish solver coverage. See the [exact GPU receipt](discovery/gpu.md).

**Owner decision needed before further numerical discovery:** approve one fixed discovery-only GPU profile with 8 GiB AS, retaining the 12 MiB file limit, nonroot sanitized fresh children, fixed synthetic cases and one SkyPilot-scheduled GPU. Keep CPU numerical children at 3 GiB AS. Keep production worker policy unchanged. Record actual host RSS/VRAM, precision, native coverage and cold/warm CPU comparisons; failure at 8 GiB remains a failure and does not authorize another increase. The existing $25 total budget and SkyPilot teardown still apply. This changes the isolation assumption in TASK-005 and therefore needs explicit owner approval before numerical execution at the larger limit.

A production GPU execution profile remains a separate later G1 decision supported by actual native measurements. Do not remove the AS limit, accept an unbounded override, or treat QuTiP's CuPy storage / CPU fallback as GPU solver support. JoSIM remains CPU absent a supported native implementation.

For production, queue when a compatible GPU placement is unavailable. CPU fallback is permissible only if an explicit server policy admits the same request under CPU bounds, preserves precision/solver semantics and records the actual backend. Worker reuse must match the exact image, profile, device/precision compatibility and policy version, with restart-safe durable ownership. Clients cannot select raw resources or native backend names.
